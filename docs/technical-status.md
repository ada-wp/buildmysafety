### Pending-deletion operator runbook

The preview uses user retry plus **manual operator follow-up**. This is not an automatic retry job, monitoring service or Clerk deletion webhook. A real staging check at `2026-10-12T18:24:33.556Z` found **0 pending receipts**.

1. Before a preview release and during supervised pilot operations, run from `app/`: `node scripts/check-pending-deletions.mjs <installed-wrangler-bin/wrangler.js>`. It uses existing Wrangler authentication and reads only the configured staging database. Exit 0 means none pending, 2 means follow-up is needed, and 1/other failure means the check failed, not that the count is zero. Logs contain only counts and the oldest request time.
2. If pending, inspect at most 20 `account_deletions` rows ordered by `requested_at` in the trusted Cloudflare staging console, selecting only `user_id`, status and timestamps. Keep IDs out of public logs, screenshots and reports. Check the configured Clerk **development instance**; do not identify an account by email similarity or switch environments to find it.
3. When the owner still has an active account, the in-app Privacy retry is the normal path. Its authenticated handler reuses the durable deletion receipt and repeats the exact owner's identity deletion. Do not ask them to submit their answers again or recreate the profile.
4. If Clerk already removed the exact identity but the final D1 receipt update failed, verify both that identity's absence in the matching instance and zero owned rows in `memory_profiles`, `onboarding_progress`, `memory_task_states`, `memory_private_task_content`, `memory_completion_awards`, `memory_latest_batch` and `memory_ai_attempts`. A timeout, wrong instance or permission error is not evidence of absence. Only after those checks may an operator mark that single pending receipt `deleted` with a completion timestamp. Retain the receipt and do not alter shared task content.
5. If the Clerk identity still exists and self-service retry is unavailable, reconcile that single account only against its durable deletion request and verified identity/environment. Never run a blanket deletion or mark a receipt complete while the identity or owned app rows remain. Record the operational outcome without answers, content or credentials; rerun the aggregate check.

Public release still needs an assigned operator/check cadence or automated reconciliation with alerts, a reviewed retention policy, and a procedure for direct Clerk dashboard deletions (which currently do not erase D1). This runbook/checker makes preview follow-up concrete; it does not claim unattended deletion recovery. Separate production identity/data, content approval, urgent/out-of-scope evaluation and full device/load checks remain required. Step 10's bounded preview reliability pass is finished, not the public launch checklist.

## Meaningful checks before beta

- New batches preserve saved tasks and exclude already shown action keys; malformed/failed AI responses are recoverable without erasing state.
- The server accepts only resource IDs present in a reviewed, eligible catalog and returns validated URLs. Check dead links and region restrictions.
- Task reads and writes enforce ownership; two different accounts cannot access each other's tasks. Include deletion/export and minimal retention.
- Completion awards are idempotent. Undo and repeated requests cannot multiply growth; there is no penalty for absence.
- Test touch, keyboard, expansion versus completion, loading/error/empty/exhausted states and mobile widths.
- Cap per-user and global generation costs; record safe operational metrics without raw private inputs. Load test the expected pilot size, not hypothetical scale.
- Only describe reminders as working after permissions, scheduling, timezone, cancellation and deep links pass on supported devices.
