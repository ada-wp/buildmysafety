## Purpose

Primarily help women living solo build a sense of agency, safety and control through practical knowledge, preparation, supportive connections and chosen actions. Living solo remains the core audience and context, as Ada reconfirmed on October 1; the purpose includes enjoying life and trusting one's ability to act, not just household upkeep. Each visit should make one useful action feel possible. Follow [founder voice](founder-voice.md); do not frame solo living as a problem, manufacture fear or imply guaranteed protection.

Onboarding adds focus; it does not determine or restrict the whole experience. The person's current topic, selected concerns and explicit request take priority over earlier answers. Keep all supported topics accessible and editable. Ada also requested restrained AI use: reviewed solution pools and simple selection rules should supply ordinary recommendations; generative AI is reserved for meaningful gaps or adaptations.

Latest clarification, October 11: accumulated memory should help with her **next question or problem**, not assume every visit continues the same problem. Use only relevant prior context and reusable preferences; keep the new question in charge. The before/after paid test repeated one request to isolate memory effects, not to define the product's normal journey. Ada also agreed with tightening duplicate-suggestion checks.

Longer-term direction, clarified October 11: Ada wants an agent whose suggestions improve through feedback, become more individualized, and eventually serve additional audiences. Women living solo remain the initial audience. Build toward two separate loops: editable personal context for better individual fit, and reviewed examples/evaluations for better shared recommendation quality. A reusable library supplies knowledge and proven content; relevant retrieval, variants and bounded generation allow personalization. This does not require generation on every interaction or automatic model training. The [personalization plan](personalization-plan-v0.md#continuous-improvement-and-future-audiences) separates these loops. A narrow personal-memory implementation now exists in hosted staging; an automated shared-quality learning system has not been built.

Ada specifically wants liked tasks and tasks added to My list to influence future related suggestions. Use these as soft signals of interest and intent, then prefer useful new outcomes within the person's current topic and constraints. Like, save and completion have distinct meanings; none proves the task worked or establishes a permanent preference alone. Ordinary matching uses stored tags and rules without a model call. The connected + action now supplies save signals. A Like control and user-facing preference reset remain later work; neither is needed to save or complete a task.

## Content and AI

Ada approved the [writer prompt's usefulness definition and six angles](prompts/task-writer-v1.1-draft.md#proposed-developer-prompt) on October 11: a completed task should leave a usable decision, option, preparation, skill or access to support. Understand, Discover, Prepare, Arrange, Practice, and Make it easier next time guide suggestion selection according to the actual gap. They are not new app categories or a mandatory sequence. This addition was tested in the [new-neighborhood scenario](prompts/evaluations/2026-10-11-new-neighborhood-test.json): three distinct tasks, checked resource IDs and passing format checks, with editorial notes to make the research instructions more concrete. This one synthetic run is awaiting founder review and does not approve pool publication or production activation.

AI remains a supported capability, not a requirement for every batch. Ada's latest decision permits one automatic useful adaptation alongside pool tasks, within the existing total of three. Decide from current needs, relevant memory and supported guidance; a pool having available tasks does not by itself rule adaptation out. Mere rewording, inserting a name or filling an empty slot does not justify a call. When it adds no value, use pool tasks. Opening details, saving, navigation and elephant feedback never need AI. The preview enforces quotas, immutable private accepted content and validation/fallback behavior; missing guidance is not permission to invent advice.

After the new-neighborhood test, Ada clarified that **at most one suggestion in a batch may contain external links**. It need not be the first suggestion, and a batch may have none. The one linked task can include up to two relevant checked resources, each with a clear purpose and a specific way to use it; other tasks have no resource links and offer complementary actions. This replaces the assistant's mistaken interpretation that the first task should have links. The candidate prompt and server validator now enforce this rule in the memory/API implementation. The original neighborhood test attached resources to two tasks and would fail the cap; its historical output remains unchanged.

Ada also rejected the dull, dry suggestion tone and requested livelier, more personal writing. The candidate prompt now uses conversational titles and summaries, known context that genuinely shapes the action, and short clear steps. An editorial rewrite of the new-neighborhood batch is saved for review. This updates the writing direction; it is not a new model test, production activation or approval of the sample tasks.

For task-copy review, Ada reaffirmed the original format: **title · time → three numbered steps → Done when**. Keep warmth and personalization within that compact structure, and present the steps rather than only a prose overview. This is a writing/presentation preference; the existing JSON fields and UI are unchanged. The later paid memory-comparison tests used the then-current candidate instructions, but did not establish production writing quality; the final outcome-group correction has not had a new model test.

Historical clickable designs use fixed samples as references. The active app now matches the sick-day collection through the authenticated cloud API. Ada approved the [task-generator V1 prompt](prompts/task-generator-v1.md) on September 30. Its text remains the approved baseline for an actual generation call, not a requirement to call the model for every recommendation. It has not been connected to the live generator or evaluated through the paid API. The private one-task adaptation flow is implemented for sick-day preparation. Broader topics still need content and evaluation. The requirements below continue to apply.

Latest working sequence: Ada asked to revisit the writing prompt and teach/test the AI first, then create the solution pool. The [V1.1 calibration draft](prompts/task-writer-v1.1-draft.md) and synthetic teaching/test cases support that review. The [October 11 first real test](prompts/evaluations/2026-10-11-sick-day-smoke-test.json) used instructions alone with GPT-6 Luna in OpenAI Playground. Ada rejected the generic help-request task: when the person needs outside support, help her discover one or two useful external resources, compare relevant criteria and save an option for later. This applies across needs, not just Taskrabbit. A [second real test](prompts/evaluations/2026-10-11-urgent-pet-care-test.json) used the revised prompt with a fictional US cat owner away from home who needed care urgently. It returned two tasks and both supplied resource IDs, but lacked a clear fallback when no sitter could help. Urgent-help behavior needs a separate reviewed decision; this test does not expand the V0 into an emergency service. Food-availability wording from the first test also needs correction before reuse. The eight development and four reserved cases have not run. V1.1 is not activated; V1 remains preserved. Calibrating content creation first does not change the later pool-first runtime behavior.

- Generate preventive actions that can be taken now, tailored to selected needs and feasible time, energy, budget and support. Do not assume money, a nearby helper, a car or good health.
- Prefer small practical steps, explicit help-request messages, existing supplies, official guidance and ways to evaluate local services. Do not equate browsing a directory with confirmed help.
- Start with a curated resource catalog. The model returns resource IDs; the server validates and attaches approved URLs. Do not accept invented links. Research records are candidates, not a professionally reviewed production catalog.
- Validate structured output, relevance, duplication, length, duration and resource eligibility before display. Keep reviewed fallbacks for invalid output or outages. A useful refusal/redirect is better than unsafe advice.
- Do not diagnose, prescribe, offer hazardous DIY/security tactics or behave as an emergency service. Immediate-danger inputs require a short region-appropriate redirect, not an ordinary task batch. The content handling needs review before public release.
- Mental/body options stay optional and gentle. No treatment claims or claims that calmness proves safety. The first practical sick-day path can be tested without expanding into therapy.
- Never collect passwords, recovery codes, precise home access instructions or unnecessary medical details. Do not use private concerns in analytics or model-facing design-state summaries.

The implemented task contract separates stable action/content references, shared instructions/resources, user task state, latest batch recovery and unique completion awards. Generation, resource lookup, storage and UI remain separate so private adaptations can be added without changing saved pool instructions.
